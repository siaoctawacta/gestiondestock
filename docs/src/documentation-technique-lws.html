Chapitre 1

Objet du document et architecture

Ce document décrit pas à pas la mise en ligne de l'application de gestion de stock MM Cosmétiques chez l'hébergeur LWS, puis son exploitation au quotidien.

Les deux parties de l'application

Le dépôt contient deux projets indépendants, qui s'hébergent différemment :

PartieContenuHébergement
Frontend
frontend/		L'application que les utilisateurs ouvrent dans leur navigateur (React). Une fois construite, ce n'est qu'un dossier de fichiers statiques : frontend/dist/.N'importe quel hébergement web : l'hébergement LWS cPanel suffit.
Backend
backend/		Un projet Supabase : base PostgreSQL, authentification des utilisateurs, API REST, temps réel, stockage des images, fonctions serveur (Edge Functions), règles de sécurité par boutique (RLS).Supabase Cloud, ou Supabase installé sur un VPS (Docker).
Point essentiel L'hébergement web mutualisé de LWS fournit une base PostgreSQL, mais une base seule ne suffit pas : l'application a besoin de toute la plateforme Supabase (connexion des utilisateurs, API, temps réel, fonctions serveur). C'est pourquoi la base est soit sur Supabase Cloud, soit sur un VPS LWS qui fait tourner Supabase.

Schéma de fonctionnement

Mode démo et mode production

Le frontend choisit son mode au moment du build, selon le fichier frontend/.env :

  • avec VITE_SUPABASE_URL et VITE_SUPABASE_ANON_KEY renseignées : production, les données sont dans Supabase ;
  • sans ces variables : mode démo, avec des données fictives stockées dans le navigateur et un bandeau jaune « Mode démo » en haut des pages.
À vérifier à chaque mise en ligne Si le site de production affiche le bandeau « Mode démo », il a été construit sans les variables Supabase : les ventes saisies resteraient dans le navigateur du poste et seraient perdues. Reconstruisez le site avec le bon .env avant toute utilisation.

Chapitre 4

Option A — Hébergement web LWS + Supabase Cloud

Le site est hébergé par LWS ; la base de données et l'authentification sont fournies par Supabase Cloud.

4.1 Créer le projet Supabase

  1. Créez un compte sur supabase.com, puis un nouveau projet. Choisissez une région proche (par exemple West EU) et un mot de passe de base robuste : notez-le dans un gestionnaire de mots de passe.
  2. Dans Project Settings → API, notez l'URL du projet (https://<ref>.supabase.co) et la clé anon public. Le <ref> est l'identifiant de 20 lettres dans l'URL.
  3. Dans Project Settings → Database → Connection string, copiez la chaîne de connexion (format URI) : elle sert à charger les données de départ et aux sauvegardes.

4.2 Installer la base de l'application

CLI Supabase version 3 Depuis la version 3, supabase db push et supabase db dump agissent sur une base locale par défaut. Pour agir sur le projet en ligne, ajoutez toujours --remote. Sans cette option, la commande ne modifie rien sur votre base de production.

Depuis le dossier du dépôt, sur votre poste :

cd backend
supabase login
supabase link --project-ref <ref-du-projet>

# Crée les tables, fonctions, déclencheurs et règles de sécurité (dans l'ordre des migrations)
supabase db push --remote

# Données de départ : boutiques, catégories, fournisseurs, produits — UNE SEULE FOIS, sur une base vide
psql "<chaîne de connexion>" -f supabase/seed.sql

# Fonctions serveur : gestion des comptes, validation superviseur des remises
supabase functions deploy admin-users
supabase functions deploy verify-supervisor
Ce que contient la base Les migrations (backend/supabase/migrations/) créent les 19 tables, les fonctions métier (vente, transferts, déclarations…), les déclencheurs d'audit et d'alertes, et active la sécurité par boutique (RLS) sur toutes les tables. Le fichier seed.sql ne contient que les référentiels : aucun utilisateur, aucune vente. Adaptez-le à vos boutiques et produits réels avant de le charger, ou créez-les ensuite depuis l'application.

4.3 Créer le premier Super Admin

  1. Dans Supabase : Authentication → Users → Add user. Saisissez l'email et un mot de passe, et cochez Auto Confirm User.
  2. Dans SQL Editor, donnez-lui le rôle Super Admin : 
    update public.users
   set role_id = 'super_admin', first_name = 'Prénom', last_name = 'Nom'
 where email = 'vous@mmcosmetiques.com';
  3. Tous les autres comptes se créent ensuite depuis l'écran Utilisateurs de l'application, par ce Super Admin.

4.4 Configurer l'authentification

Dans Authentication → URL Configuration :

RéglageValeur
Site URLhttps://stock.mmcosmetiques.com
Redirect URLshttps://stock.mmcosmetiques.com/reset-password (lien « mot de passe oublié »)

Pour que les emails de réinitialisation partent de votre domaine, renseignez votre serveur SMTP dans Authentication → SMTP Settings (l'envoi par défaut de Supabase est limité). Désactivez l'inscription libre (Allow new users to sign up) : les comptes sont créés par le Super Admin.

4.5 Construire le site

Les clés Supabase sont intégrées au site au moment du build : construisez sur votre poste, pas sur le serveur.

cd frontend
cp .env.example .env
# Éditez .env :
#   VITE_SUPABASE_URL=https://<ref>.supabase.co
#   VITE_SUPABASE_ANON_KEY=<clé anon public>
npm ci
npm run build          # produit le dossier frontend/dist/
Ne jamais publier la clé service_role Seule la clé anon va dans .env : elle est publique par nature, la sécurité reposant sur les règles RLS de la base. La clé service_role contourne toutes les règles : elle ne doit jamais apparaître dans le frontend, un email ou le dépôt.

4.6 Publier sur l'hébergement LWS

  1. Dans l'espace client LWS, ouvrez le cPanel de l'hébergement. Si vous utilisez un sous-domaine (stock.mmcosmetiques.com), créez-le dans Domaines et notez son dossier racine.
  2. Activez le certificat SSL (Let's Encrypt) pour ce domaine dans cPanel.
  3. Ouvrez le Gestionnaire de fichiers et allez dans le dossier racine du domaine (souvent public_html/). Dans Paramètres, cochez Afficher les fichiers cachés. Videz le dossier s'il contient une page par défaut.
  4. Compressez le contenu de frontend/dist/ en .zip (pas le dossier lui-même), envoyez l'archive, puis Extraire. Vérifiez la présence de index.html, du dossier assets/, des logos et du fichier .htaccess. Supprimez ensuite l'archive.
  5. Variante FTP : avec les identifiants FTP de l'espace client, copiez le contenu de dist/ dans le dossier racine (afficher les fichiers cachés dans FileZilla : Serveur → Forcer l'affichage des fichiers cachés).

Rôle du fichier .htaccess

Le fichier frontend/public/.htaccess est copié dans dist/ à chaque build. Il :

  • force le HTTPS ;
  • renvoie les adresses de l'application (/pos, /stores…) vers index.html. Sans lui, recharger une page autre que l'accueil donne une erreur 404 ;
  • ajoute des en-têtes de sécurité et règle le cache : index.html n'est jamais mis en cache, pour que chaque mise à jour soit prise en compte.
Chapitre 5

Option B — Tout sur un VPS LWS

Supabase est installé sur votre VPS avec Docker ; le même serveur publie le site. Réservez cette option à une équipe à l'aise avec l'administration Linux.

Responsabilités Supabase auto-hébergé est maintenu par la communauté. La sécurité du serveur, les mises à jour et les sauvegardes sont entièrement à votre charge. La configuration par défaut de Supabase n'est pas sûre pour la production : suivez toutes les étapes de ce chapitre.

5.1 Préparer le serveur et le DNS

  • VPS LWS sous Ubuntu, 4 Go de RAM minimum (modèle « VPS Docker » de préférence).
  • Deux enregistrements DNS de type A vers l'IP du VPS : stock.mmcosmetiques.com (application) et api.mmcosmetiques.com (Supabase).
ssh root@<ip-du-vps>
apt update && apt upgrade -y
apt install -y git postgresql-client
# Uniquement si Docker n'est pas préinstallé :
curl -fsSL https://get.docker.com | sh

5.2 Installer Supabase

git clone --depth 1 https://github.com/supabase/supabase /opt/supabase-src
mkdir -p /opt/supabase && cp -r /opt/supabase-src/docker/. /opt/supabase/
cd /opt/supabase
cp .env.example .env
sh utils/generate-keys.sh --update-env     # génère JWT_SECRET, ANON_KEY, SERVICE_ROLE_KEY, etc.
nano .env

Dans .env, avant le premier démarrage, vérifiez ou modifiez au minimum :

VariableValeur
POSTGRES_PASSWORDLong mot de passe aléatoire (à conserver dans un coffre)
DASHBOARD_USERNAME, DASHBOARD_PASSWORDIdentifiants du tableau de bord Supabase Studio
SUPABASE_PUBLIC_URLhttps://api.mmcosmetiques.com
API_EXTERNAL_URLhttps://api.mmcosmetiques.com/auth/v1
SITE_URLhttps://stock.mmcosmetiques.com
ADDITIONAL_REDIRECT_URLShttps://stock.mmcosmetiques.com/reset-password
DISABLE_SIGNUPtrue — les comptes sont créés par le Super Admin
SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS, SMTP_ADMIN_EMAIL, SMTP_SENDER_NAMEParamètres de la boîte email d'envoi (emails « mot de passe oublié »)

Le haut du fichier .env.example liste tous les secrets : n'en laissez aucun à sa valeur par défaut. Démarrez ensuite :

sh run.sh start        # équivaut à docker compose up -d --wait
sh run.sh status       # tous les services doivent être « healthy »

5.3 Fermer les ports internes

Par défaut, Docker publie sur Internet le port de l'API (8000) et ceux de PostgreSQL (5432, 6543). Seuls les ports 22 (SSH), 80 et 443 doivent être ouverts.

Piège courant Le pare-feu ufw ne s'applique pas aux ports publiés par Docker. Il faut ajouter la règle dans la chaîne DOCKER-USER : 
ip route | grep default          # repérez l'interface publique, par exemple eth0 ou ens3
iptables -I DOCKER-USER -i eth0 -p tcp -m multiport --dports 8000,5432,6543 -j DROP
apt install -y iptables-persistent && netfilter-persistent save

Le serveur web installé à l'étape suivante accède à l'API en local (localhost:8000) : il n'est pas concerné par ce blocage. Vérifiez depuis un autre ordinateur que http://<ip-du-vps>:8000 ne répond plus.

5.4 HTTPS et site web avec Caddy

Caddy obtient et renouvelle automatiquement les certificats Let's Encrypt.

apt install -y caddy
mkdir -p /var/www/mm-stock
cat > /etc/caddy/Caddyfile <<'CADDY'
api.mmcosmetiques.com {
    reverse_proxy localhost:8000
}

stock.mmcosmetiques.com {
    root * /var/www/mm-stock
    encode gzip
    try_files {path} /index.html
    file_server
}
CADDY
systemctl reload caddy

Supabase Studio est alors accessible sur https://api.mmcosmetiques.com, protégé par DASHBOARD_USERNAME / DASHBOARD_PASSWORD.

5.5 Installer la base de l'application

Dans le conteneur de la base, les connexions via localhost sont acceptées sans mot de passe : c'est pourquoi les commandes passent -h localhost. Les migrations s'exécutent avec le rôle postgres, comme sur Supabase Cloud.

git clone https://github.com/siaoctawacta/gestiondestock /opt/gestiondestock
cd /opt/gestiondestock/backend/supabase

# Migrations, dans l'ordre (les noms de fichiers sont horodatés)
for f in migrations/*.sql; do
  echo "== $f"
  docker exec -i supabase-db psql -h localhost -v ON_ERROR_STOP=1 -U postgres -d postgres < "$f" || break
done

# Données de départ : UNE SEULE FOIS, sur une base vide
docker exec -i supabase-db psql -h localhost -v ON_ERROR_STOP=1 -U postgres -d postgres < seed.sql

# Fonctions serveur : à côté du dossier « main » fourni par Supabase
cp -r functions/admin-users functions/verify-supervisor /opt/supabase/volumes/functions/
cd /opt/supabase && sh run.sh restart functions

Créez le premier Super Admin dans Studio (Authentication → Add user), puis :

docker exec -i supabase-db psql -h localhost -U postgres -d postgres -c \
  "update public.users set role_id = 'super_admin', first_name = 'Prénom', last_name = 'Nom' where email = 'vous@mmcosmetiques.com';"

5.6 Construire et publier le frontend

Sur votre poste, frontend/.env contient :

VITE_SUPABASE_URL=https://api.mmcosmetiques.com
VITE_SUPABASE_ANON_KEY=<ANON_KEY du fichier /opt/supabase/.env>
cd frontend && npm ci && npm run build
rsync -av --delete dist/ root@<ip-du-vps>:/var/www/mm-stock/

Avec Caddy, le fichier .htaccess n'est pas utilisé : la directive try_files du Caddyfile joue le même rôle.

Chapitre 6

Mise en service : vérifications finales

À dérouler avant d'ouvrir l'application aux utilisateurs, quelle que soit l'option.

Liste de contrôle technique

  • Le site s'ouvre en HTTPS, avec un cadenas valide, et http:// redirige vers https://.
  • Aucun bandeau « Mode démo » n'apparaît en haut des pages.
  • Recharger directement /pos ou /stores affiche la page (pas d'erreur 404).
  • Le Super Admin se connecte ; un compte inconnu ou un mauvais mot de passe est refusé.
  • Le lien « Mot de passe oublié » envoie bien un email, et le lien reçu ouvre la page de nouveau mot de passe.
  • Création d'un utilisateur depuis l'écran Utilisateurs : fonctionne (cela valide la fonction admin-users).
  • Une vente test en caisse avec remise de plus de 15 % demande bien la validation d'un superviseur (fonction verify-supervisor).
  • La vente test apparaît dans l'historique et le stock de la boutique a diminué.
  • Un caissier d'une boutique A ne voit ni les ventes ni le stock d'une boutique B.
  • Le ticket PDF et un export PDF / Excel se génèrent correctement.
  • Option B : les ports 8000, 5432 et 6543 ne répondent pas depuis l'extérieur ; une première sauvegarde a été faite et restaurée avec succès sur une base de test.

Liste de contrôle des données

  • Les boutiques réelles sont créées (codes, adresses, responsables) et les boutiques d'exemple inutiles supprimées.
  • Le catalogue réel est saisi : prix d'achat HT, prix de vente TTC, taux de TVA, codes-barres EAN13, seuils minimum.
  • Le stock initial de chaque boutique est saisi par des entrées de stock (avec numéro de lot et date de péremption).
  • Les comptes utilisateurs sont créés avec le bon rôle et la bonne boutique.
  • Les ventes de test sont identifiées, ou faites sur un environnement séparé.
Chapitre 7

Exploitation courante

Mises à jour, sauvegardes, restauration et consultation des journaux.

7.1 Publier une nouvelle version

Ordre à respecter quand une version modifie aussi la base : migrations d'abord, frontend ensuite.

git pull                                   # récupérer la nouvelle version

# 1. Base de données — option A
cd backend && supabase db push --remote --dry-run     # prévisualiser
supabase db push --remote

# 1. Base de données — option B (sur le VPS, pour chaque nouvelle migration)
docker exec -i supabase-db psql -h localhost -v ON_ERROR_STOP=1 -U postgres -d postgres \
  < backend/supabase/migrations/<nouveau-fichier>.sql

# 2. Frontend
cd frontend && npm ci && npm run build
# option A : remplacer le contenu du dossier racine cPanel par celui de dist/ (garder .htaccess)
# option B : rsync -av --delete dist/ root@<ip-du-vps>:/var/www/mm-stock/

Si une fonction serveur a changé : supabase functions deploy <nom> (option A), ou recopier son dossier dans /opt/supabase/volumes/functions/ puis sh run.sh restart functions (option B).

7.2 Sauvegardes

Option A — Supabase Cloud

Supabase sauvegarde automatiquement la base selon l'offre souscrite (Database → Backups). Pour une copie complète sous votre contrôle (Docker Desktop requis sur le poste) :

cd backend
supabase db dump --remote --role-only -f roles.sql
supabase db dump --remote -f schema.sql
supabase db dump --remote --data-only --use-copy -f data.sql

Option B — VPS

Les sauvegardes complètes se font avec le superutilisateur supabase_admin. Sauvegarde automatique chaque nuit à 2 h, avec 14 jours d'historique (crontab -e) :

mkdir -p /root/backups
0 2 * * * docker exec supabase-db pg_dump -h localhost -U supabase_admin -d postgres -Fc > /root/backups/mm-$(date +\%F).dump && find /root/backups -name 'mm-*.dump' -mtime +14 -delete
Copier hors du serveur Une sauvegarde qui reste sur le VPS disparaît avec lui. Copiez régulièrement /root/backups ailleurs (poste local, stockage externe), par exemple : rsync -av root@<ip-du-vps>:/root/backups/ ./sauvegardes-mm/.

7.3 Restaurer

Option A, dans un projet vide (chaîne de connexion du projet cible) :

psql "<chaîne de connexion>" --single-transaction --variable ON_ERROR_STOP=1 \
  --file roles.sql --file schema.sql \
  --command 'SET session_replication_role = replica' --file data.sql

Option B :

docker exec -i supabase-db pg_restore -h localhost --clean --if-exists -U supabase_admin -d postgres < /root/backups/mm-AAAA-MM-JJ.dump
Tester ses sauvegardes Une sauvegarde n'a de valeur que si sa restauration a été testée. Faites l'essai une fois par trimestre sur un projet ou un serveur de test, jamais directement sur la production.

Chapitre 8

Sécurité

Principes intégrés à l'application, et règles à respecter côté hébergement.

Ce que l'application garantit

  • Sécurité par boutique (RLS) activée sur toutes les tables : un utilisateur ne lit et n'écrit que les données de ses boutiques, même en appelant l'API directement.
  • Aucune écriture directe sur le stock, les ventes, les transferts ou les déclarations : tout passe par des fonctions de la base qui vérifient le rôle et la boutique.
  • Les totaux de vente sont recalculés par la base à partir des prix du catalogue : un poste modifié ne peut pas changer un prix.
  • Le journal des mouvements de stock et le journal d'audit sont inaltérables.
  • Seul le Super Admin crée, modifie ou supprime des boutiques et des comptes et attribue les rôles.

Règles d'exploitation

ÉlémentRègle
Clé service_role / SERVICE_ROLE_KEYJamais dans le frontend, un email, une capture ou le dépôt Git. À régénérer si elle a fuité.
Fichier .envJamais dans le dépôt (déjà exclu par .gitignore). Sur le VPS : chmod 600 /opt/supabase/.env.
Mots de passeGestionnaire de mots de passe ; un compte par personne, jamais de compte partagé en caisse.
Départ d'un employéDésactiver ou supprimer son compte le jour même (écran Utilisateurs).
Accès SSH (option B)Connexion par clé SSH, puis désactiver la connexion root par mot de passe.
Super AdminsEn limiter le nombre (deux personnes de confiance) ; l'application empêche de retirer le dernier.
SauvegardesQuotidiennes, copiées hors du serveur, restauration testée chaque trimestre.
